# Пауза перед ответом и стабильность длинной речи

Локальный сервер передаёт первое проверенное предложение в Piper/RVC сразу,
пока LLM продолжает ответ. Пока отправляется готовый звук, синтезируется следующая
фраза. Порядок сохраняется; внутри одного ответа синтез выполняется последовательно.
Очереди ограничены двумя текстовыми фразами и одной готовой аудиофразой.

Проверки повторов и шаблонных ответов выполняются перед озвучкой каждой фразы.
Плохое начало можно перегенерировать один раз. Если повтор обнаружен после принятой
фразы, оставшийся текст отбрасывается: уже начатый ответ не перезапускается.
Тембр RVC и параметры обработки звука сохранены. Без границы предложения начало
озвучки по-прежнему ждёт завершения текста. При отмене текущий вызов синтеза в
рабочем потоке может завершиться, но асинхронные работники ответа останавливаются.

## Почему длинный ответ мог превращаться в шипение

Ранее сервер отправлял 100 мс звука каждые 55 мс после начального пакета.
Буфер ESP32 постепенно заполнялся. Кольцевой буфер резервирует один байт,
поэтому при нехватке места прежний код мог записать нечётное число байтов и
отбросить остаток. PCM16 состоит из двухбайтовых отсчётов: такая запись сдвигала
границы всех последующих отсчётов и портила звук.

- Запись и чтение теперь сохраняют только целые отсчёты PCM16.
- Сервер выдерживает скорость 24 000 отсчётов/с с опережением до 0,5 с.
  Один планировщик используется для всех предложений ответа. Это ограничение
  отправителя, а не измерение фактической очереди на ESP32.
- Читатель повторно проверяет доступные данные под блокировкой: одновременный
  сброс больше не позволяет продвинуть указатель чтения по пустому буферу.
- Начало новой записи очищает остатки звука даже после снятия флага `speaking`.
- Последний двухбайтовый отсчёт короткого ответа тоже воспроизводится.

Тест воспроизводит потерю выравнивания старым алгоритмом и проверяет исправленный.
Это объясняет описанный симптом, но проверка реального звука на плате необходима.

## Измерения и проверка

Логи `[Latency]` показывают время от начала обработки `response.create`:
`stt_done`, `first_llm_sentence`, `first_accepted_sentence`,
`first_sentence_audio_ready`, `first_pcm_sent`, `turn_done`.
Отдельные строки `voice` показывают длительность Piper, RVC и всего синтеза.
`first_pcm_sent` — отправка сервером, а не момент слышимого звука; сеть,
буферизация и включение динамика добавляют задержку.

Проверки без моделей и платы из корня firmware:

```text
python -B -m unittest discover -s tests -p test_speech_pipeline.py -v
g++ -std=c++17 -fsyntax-only tests/pcm16_buffer_test.cpp tests/bender_face_state_test.cpp
```

Python-тесты проверяют раннюю отправку, порядок фраз, ограничение очередей,
отмену, ошибки, фильтры и протокол команд. Минута PCM проверяется с виртуальными
часами: байты не меняются, опережение не превышает 0,5 с.

Для применения обновить прошивку и перезапустить локальный сервер. Затем:

1. Попросить длинный ответ с речью более минуты и проверить отсутствие шипения
   и сообщений `[AI] ring full` в Serial.
2. Сразу задать новый короткий вопрос, затем прервать следующий ответ кнопкой
   и начать новый разговор. Проверить чистый звук и отсутствие старого хвоста.
3. Проверить голосовую команду, короткий ответ и обычный разговор; сравнить
   `[Latency] first_pcm_sent` на нескольких похожих вопросах.

Реальная экономия времени до первого слышимого слова пока не измерена.
