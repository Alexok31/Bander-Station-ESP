# Задержка ответа: проверка 11 октября 2026

Исправлена повторная загрузка модели RMVPE внутри RVC. Она определяет высоту
голоса; установленный Applio создавал сеть и читал её веса при каждой фразе,
хотя сам процесс RVC уже был постоянным. В профиле были повторные вызовы
`RMVPE0Predictor.__init__`, инициализация свёрточных слоёв и `torch.load`.

Теперь `rvc_runtime.PitchPredictorCache` удерживает одну сеть в последовательном
RVC worker. При изменении пути, размера/времени изменения весов или устройства
кэш заменяется. Настройки RMVPE, включая high-register, продолжают читаться
обычным кодом Applio. Файлы установленного Applio не изменены.

## Измерения

ПК: RTX 4070 Ti 12 GB. Текущий Holos CPU INT8, Speaker_84, delivery=standard,
speed=1.14; RVC pitch=-3, index_rate=0.55, RMS=0.75, protect=0.33, RMVPE.
Основной сервер оставался запущен; измерения моделей выполнялись отдельно,
последовательно, без воспроизведения звука.

Четыре фиксированные фразы, три прохода до и после. Первый проход исключён
из тёплой статистики: восемь измерений на вариант.

- Подготовка всей озвучки, медиана: **1386 → 817 мс**, сокращение на 41%.
- Сам RVC, медиана: **755 → 198 мс**.
- Holos, медиана: 514 → 522 мс; он не изменялся.
- Подготовка ударений, медиана: 84 → 87 мс; она не изменялась.

Медианы отдельных этапов не обязаны складываться в медиану суммы.
Холодный запуск отдельного тестового процесса занял около 9–10 секунд;
ускорение относится к прогретой системе. Сервер прогревает RVC при запуске.

Дополнительно выполнены три изолированных диалоговых запроса через настоящий
Whisper CUDA large-v3-turbo и Grok grok-4.3. Вход — синтетическая украинская
речь. Внешние запросы использовали только тестовый промпт, пустую память и
вымышленные вопросы. Пользовательская история, память и настройки характера
не отправлялись и не изменялись.

Для повторного прогона сохранены текстовые дельты Grok и время их поступления:
после оптимизации воспроизведён тот же поток, без новых запросов к модели.
ASR и синтез выполнялись заново. Это сравнение локальной обработки на одинаковом
ответе, а не доказательство ускорения самого Grok.

- Время до первого PCM: **2855 → 2214**, **2560 → 1915**, **2255 → 1826 мс**.
- Медиана: **2560 → 1915 мс**, сокращение на 25%.
- История тестового ответа в каждой паре совпала.

Отсчёт начинается с `response.create` на сервере. Он не включает речь человека,
ожидание тишины на ESP32, передачу записи, сеть до колонки и аппаратный старт
динамика. На момент замеров окончание фразы требовало 800 мс тишины.
По запросу пользователя в `WakeVoice.h` порог затем сокращён до 400 мс
для первого вопроса и продолжения разговора. Это требует прошивки ESP32;
ожидаемый выигрыш — ещё 400 мс при уверенном определении тишины.
Пауза внутри вопроса длительностью 400 мс тоже может завершить запись.
С этими замерами нельзя обещать пользователю звук ровно через 1,9 секунды после
последнего слова. Полноценная проверка микрофон → динамик остаётся на устройстве.

## Сохранность голоса и устойчивость

- 20 извлечений высоты голоса с чередованием четырёх длин: расхождение
  относительно исходного алгоритма меньше 0,001 Гц, voiced/unvoiced кадры совпали.
- Занятая GPU-память в этой серии оставалась 356,14 MiB. Само удержание RMVPE
  добавляет около 347 MiB относительно состояния без её весов. Это постоянный
  расход вместо загрузки/удаления сети при каждой фразе.
- Контрольный RVC-тест с одинаковым PCM и одинаковой случайностью вокодера:
  длины совпали, корреляция сигналов не ниже 0,99999959. Для проверки использованы
  сохранённые WAV как одинаковый вход обеих ветвей; это контроль алгоритма,
  а не оценка субъективного сходства с Бендером.
- Независимая ASR-проверка четырёх полностью синтезированных фраз дала по три
  ошибочных слова суммарно в каждом варианте. Отдельные слова различались
  (например, «останнє/остальне»); такая проверка сама по себе не доказывает
  идентичность произношения. Контролируемый тест выше отделяет влияние кэша от
  стохастики озвучки. Ударения и все голосовые параметры сохранены.
- Четыре теста жизненного цикла кэша и 38 существующих тестов голосового
  конвейера прошли.

Число потоков FAISS, кэш его индекса и отключение очистки CUDA allocator
исследовались отдельно, но устойчивого выигрыша не показали. В рабочий код
эти изменения не внесены. Нарезка фраз на произвольные куски также не применялась.

## Применение

На работающем сервере перезапущен **только дочерний RVC worker**. Основной процесс,
соединение с Grok и пользовательская история не перезапускались. Новый worker
прогрет через отдельный локальный WebSocket с пустым входом: срабатывает локальная
реплика «не расслышал», без LLM и записи в историю. Два ответа завершились,
после каждого получен `pong`. Аудио принималось диагностическим клиентом и
отбрасывалось — колонка его не воспроизводила.

Исправление активно; прошивать ESP32 не требуется. Дополнительное поле
`prepare=...ms` в серверном логе появится после следующего обычного запуска
основного сервера. Оно отделяет подготовку текста от времени самого TTS.

Для временного отключения кэша: `RVC_CACHE_PITCH=0` в окружении перед запуском
сервера. Текущие настройки Holos/RVC при этом сохраняются.

## Воспроизведение проверки

Из корня firmware:

```text
python -B -m unittest discover -s tests -p test_rvc_runtime.py -v
python -B -m unittest discover -s tests -p test_speech_pipeline.py -q
python -B agent-tools/benchmark_voice_latency.py --output artifacts/voice-benchmark --rounds 3
```

Для baseline используется `RVC_CACHE_PITCH=0`, для нового варианта — `1`.
`agent-tools/benchmark_dialogue_latency.py` выполняет три синтетических сетевых
диалога и воспроизводит их поток локально; требует ключ Grok и оплачиваемые API-вызовы.
В тестовой среде используется системное доверенное TLS-хранилище с включённой
проверкой сертификатов. Рабочая настройка TLS сервера не менялась.

Все исходные результаты находятся в `artifacts/voice-latency-20261011/`:
`baseline/results.json`, `pitch-cached/results.json`, `dialogue/results.json`,
`dialogue/grok_deltas.json`, `pitch-verification/results.json`,
`pitch-verification/controlled-audio.json`, `pronunciation.json`,
`live-worker-check.json`, `summary.json`.

Вывод: задержка зависела не только от последовательности четырёх этапов.
Повторная инициализация вспомогательной сети отнимала заметную долю времени
каждой реплики. После её устранения значимыми остаются ожидание конца вопроса,
первого законченного предложения Grok и синтез Holos.
